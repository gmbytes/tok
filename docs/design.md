# tok 游戏服务器框架设计草案

tok 是一个使用 Rust 开发的游戏服务器框架。框架围绕业务 ID 组织服务路由与业务抽象，分离局外逻辑和局内场景流量，最终通过一个二进制和不同配置部署不同服务。

本文记录当前设计约定、业务与框架的职责边界，以及后续设计范围。当前以局外执行模型和服务通信为主，存储细节与无缝场景切换留待后续设计。

第二批单进程客户端接入及第三批恢复的分帧、登录、session 状态、重复登录与容量约定见 [局外 TCP 协议与 session 实施约定](client-session.md)。第三批已接通 timer 调度、ACK 缓存与同网关恢复，默认断线宽限期 30 秒；跨网关交接仍待实施。

## 设计范围与术语

框架负责服务组合、发现与路由、网关接入、session 驱动、内部 RPC、事件和协议扩展。游戏负责具体 protobuf 消息、业务处理、登录认证逻辑、离线恢复模式及跨实体一致性。

node_id 标识部署节点，service_name 标识节点内的业务服务，两者组合用于服务发现、定位和运维；bid 标识业务实体，用于业务路由与互斥；消息 ID 选择消息类型与处理函数；request_id 关联请求与回应；session_id 标识可恢复的逻辑会话。这些标识具有不同职责。

所有服务统一通过 (node_id, service_name) 定位，无需单独的服务实例 ID。node_id 的集群唯一性由部署和注册发现机制保证；service_name 在同一节点内唯一，不同节点可以使用相同的服务名。当前配置在进程级设置 node_id 和 endpoints，各服务配置 service_name 和 endpoint 引用；配置校验保证节点内服务名及端点名唯一、引用有效，内存目录按 (node_id, service_name) 注册和注销。集群节点身份的获取与校验在生产注册发现实现时细化。

一个服务可以处理多个业务 bid，同一个 bid 可以在不同时间或请求中由不同节点上的服务处理。例如 player 服务处理多个 player id，公会服务处理多个 guild id。网关、管理器和协调器也通过节点和服务名定位，但不要求每次调用都以某个具体业务实体的 bid 为目标。业务互斥使用服务命名空间和 bid 作为锁键，以便跨节点访问同一业务实体时仍共享互斥范围。

部署节点、节点内服务与业务实体分别通过 node_id、service_name 和 bid 标识。服务名由游戏定义，启动工厂注册和服务发现均以 service_name 为依据。例如 guild 和 mail 各自注册实现、分别查询节点，不要求框架预定义服务类型。相同业务服务在各节点使用一致的服务名，以便发现和路由。

player 无状态指处理能力不依赖某个常驻 player 实例或客户端连接，业务数据仍然存在，读缓存也可以存在。网关 session 是有状态的，持有会话身份、执行顺序、timer 调度和补发记录。

局内与局外描述业务职责，接入协议与安全实现均可替换。下文列出的 TCP、HTTP、WebSocket、KCP、TLS 和 DTLS 是适配示例，不代表初期必须实现全部适配。

## 业务 ID 与路由

任何游戏业务都有具体的业务 ID，统称为 bid。业务可以使用自己的名称，例如 player id、guild id、scene id。业务的路由分类和抽象都以对应的 bid 为依据。

PlayerGateway通过计算 player id 的 hash，选择处理该玩家业务的游戏节点。玩家访问公会等实例服务时，使用目标实例的 bid 路由到对应服务。

服务发现提供节点信息，路由组件结合 bid 的 hash 提供节点亲和性，提高读缓存命中率。亲和性是优化能力，并非所有服务的强制要求。

## 服务分类

| 类型 | 职责 | 示例 |
| --- | --- | --- |
| 全局管理服务 | 创建和管理业务实例，处理少量涉及多个实例的业务 | 公会管理器 |
| 全局实例服务 | 处理具体 bid 对应的实例业务，通过请求级分布式锁避免竞态 | 公会实例 |
| PlayerGateway | 维护客户端连接和玩家 session，串行驱动局外 player 逻辑 | 玩家请求入口 |
| SceneGateway | 维护局内流量，对接场景服务器，未来支持协调无缝场景切换 | 战斗或大世界入口 |
| 协调服务 | 协调业务流程与服务资源 | 场景匹配器 |
| 场景服务 | 执行局内场景逻辑 | 战斗场景、MMO 世界场景 |

player 服务部署在游戏节点上，负责玩家的局外游戏逻辑。其执行入口和状态访问约定见下文。

## 客户端接入与网关

### 统一 Gateway 组装校准

网关采用统一运行框架，按配置选择接入组件。Gateway 负责监听适配、连接容量、后台任务启动与监督、退出收束；PlayerIngress 负责登录协议、玩家所有权、串行 session 与 player RPC；Scene 接入组件后续负责场景定位和异步场景消息，不复制独立网关运行循环。

PlayerGateway 与 SceneGateway 在下文表示两类业务角色，不要求两套独立运行时实现。PlayerGateway 的已有 Rust 接口保留为统一 Gateway 的兼容包装；新组装通过 Gateway 与接入组件完成。游戏按名称注册初始化工厂，服务默认按 service_name 查找，可通过可选 factory 字段选择其他名称的工厂；service_name 始终用于服务身份，同一工厂可创建多个不同身份的服务。ServiceConfig 不包含网关专用选择项；具体组件的协议及端点共享约束由组装层检查。同一二进制可以配置多个独立入口，按需拆分部署。

协议、认证、session 和恢复语义由组件明确，不在通用 Gateway 中到处判断 player/scene。初期提供 TCP 监听适配和 PlayerIngress；Scene 仍未实现，选择它时必须明确报错。通用传输契约不假定所有适配都是 TCP；未来 UDP/KCP 需提供自己的接入适配，不强行沿用逐连接读写流程。

重构验收保持现有认证、串行执行、下行顺序、容量拒绝、租约失效与退出清理行为，并验证自定义组件能够复用运行时、业务服务名可独立配置、后台与连接任务异常可被统一监督。

### PlayerGateway（玩家网关）

客户端通过可替换的接入协议访问PlayerGateway，可以采用 TCP、HTTP、WebSocket 等。PlayerGateway为玩家维护逻辑 session，并根据 player id 的 hash 选择游戏节点。

session 串行执行客户端请求，通过调用游戏节点上的 player 服务完成局外业务逻辑。

同一个 player 在整个网关集群中的有效 session 按所有权租约协调。Redis 后端已提供原子获取、epoch 更新、条件续租和释放；玩家重连到其他网关时，新网关需要先获取该 player 的 session 所有权，再驱动 player 执行。当前网关拒绝接管其他网关的活动租约，正常释放或过期后可建立新会话，完整交接仍待实现。

重复登录根据当前会话状态尝试增加所有权 epoch，踢出旧 session 并获取所有权。所有权变更需要原子地检查当前状态并更新 epoch，旧 session 不再作为有效的执行入口。epoch 标识所有权代次，与标识逻辑会话的 session_id 分开。

```text
客户端 request
    → PlayerGateway session
    → 按 player id 路由
    → 游戏节点 player 服务
    → response 返回客户端
```

### SceneGateway（场景网关）

SceneGateway维护局内流量，并连接到玩家所在的场景服务器，消息以异步方式处理。接入协议可替换，KCP 或 UDP 是可选实现。

局内与局外的分类依据业务职责和执行语义，不绑定具体网络协议。两类网关可以按配置组合适合的接入与安全组件。

未来支持 MMO 无缝大世界时，SceneGateway还将负责协调场景切换。当前不设计无缝切换协议。

```text
客户端局内消息
    → SceneGateway
    → 对应场景服务器
```

## player 执行模型

player 服务采用无状态的执行模型，不要求 player 常驻或依赖客户端持续在线。player 可以维护读缓存，但缓存不改变无状态的服务约定；持久化与缓存细节后续单独设计。

当前设计以全局唯一的局外 session 串行驱动作为 player 状态访问的基础。在这个约定下，player 对自身数据的变更不需要业务锁。

所有驱动 player 执行的来源，包括客户端业务请求、timer 和转发事件，都进入同一个 session 执行序列。其他服务不能绕过PlayerGateway直接调用 player。认证、重连和确认等网关控制消息由接入与会话组件处理。

player 可以调用其他服务完成业务。由于 player 通常是较大的服务，可以通过本地事件解耦内部模块；本地事件也可以纳入统一的事件抽象，其处理不能绕过 session 驱动的串行边界并发修改 player 数据。

### 离线事件

转发事件默认不拉起离线 player。超过断线宽限期的玩家默认不消费事件，也不为其等待下次登录而积压事件。只有个别业务确实需要离线执行时，才设置加载离线玩家选项，强制加载 player 完成业务；这类处理仍遵守网关 session 所有权与串行驱动约定。

绝大多数通知 player 的事件应采用登录时可恢复的业务模式。具体恢复逻辑由业务负责，框架不要求为所有离线事件自动激活 player。

### timerSpec

player 的 timer 由 player 通过 RPC 或事件通道返回的 timerSpec 确定。通常在登录时一次性提供需要的 timer，后续不要求持续返回 spec；确有动态需求时允许更新或取消。

session 收到 timerSpec 后，按照 spec 调度 timer，并在触发时串行驱动 player 执行。player 提供业务计时需求，session 负责调度与执行入口。

客户端只发起业务动作，不直接指定框架 timer 的 ID、执行消息、周期或结算产出。这些内容由服务端业务规则生成，随业务处理结果附带返回给 session。示例使用“开始生产”与内部“生产完成”展示该边界，不提供通用客户端 timer 配置接口。

```text
session 驱动 player 处理登录或其他 RPC 或事件
    → player 返回 timerSpec
    → session 按 spec 调度
    → timer 触发后经 session 驱动 player
```

### timerSpec 数据与更新

timerSpec 以 player 范围内稳定的 timer_id 标识 timer，包含触发处理类型、可选业务参数、首次触发的绝对时间 due_at，以及可选的周期 interval。due_at 使用 UTC 时间表达，网关在本地转换为调度等待时间。未指定 interval 时为一次性 timer，指定时为周期 timer。

登录或快速重登返回全量 ReplaceAll，替换该 session 的 timer 集合；空集合表示清空。后续可选的 Patch 只包含 Upsert 与 Cancel：同 timer_id 的 Upsert 替换原 spec，Cancel 删除对应 timer，取消不存在的 timer 为无操作。不返回 timer 更新表示保持原集合。

每次替换或取消递增该 timer 的本地调度版本。触发任务携带 timer_id、调度版本和预定触发时间；session 执行前检查版本和所有权，忽略已失效的任务，避免旧调度继续触发。

### 触发与错过时刻

timer 到期时只向 session 队列提交触发任务，实际 player 调用仍与请求、转发事件串行执行。同一 timer 至多保留一个待执行触发，不在 session 繁忙时积压多个周期任务。

一次性 timer 到期后执行一次并移除；安装时已过期的 spec 尽快入队执行一次。周期 timer 错过多个时刻时合并为一次触发，随后按原时间基准计算下一个未来触发时刻，不逐次追赶。传给 player 的参数包含预定与实际触发时间，具体业务结算由 player 决定。

timer RPC 失败按系统级错误记录日志，不自动重试该次触发。周期 timer 的后续触发是独立的调度，仍正常进行。

当前实现由业务响应返回可选 timer 更新，未增加隐式 player 登录调用。强类型请求可返回 HandlerReply，内部触发通过 CallRequest.timer 进入 CallContext.timer，并使用独立的 timer 分发表，客户端不能仅凭消息 ID 选择内部来源。每个 session 使用一个有界调度集合和调度 future，与执行循环共同监督，不按 timer 数量创建后台任务。队列满时等待一个容量许可；同一 timer 在排队及执行期间合并为一次触发。session 建立时对齐 UTC 和单调时钟，后续沿同一基准等待与报告时刻。max_timers 与 max_timer_bytes 限制数量及 ID、正文总字节；更新完整校验后原子应用，同次操作重复 ID、非法参数或超容量会关闭 session，避免继续使用旧集合。

### 重连与交接

断线宽限期内 timer 继续运行。同网关恢复沿用当前调度，不重新安装登录时的全量 spec。跨网关交接传输当前 spec、下一次触发时间、调度版本及待执行状态，新所有者接续调度，旧所有者停止产生有效触发。

旧 session 无法恢复时，通过快速重登重新取得全量 timerSpec。离线期间不维护默认 session timer，由登录业务恢复或结算相关状态，不在重新登录时自动补跑所有历史触发。

## 全局实例的请求级锁

局外业务频率较低，当前游戏设计为全局实例的每次 RPC 配置基于 bid 的请求级分布式锁，无需引入实例常驻所有者模型。这是游戏选择的服务执行策略，框架不根据服务自动强制加锁。

锁通过服务端 RPC 中间件封装：从请求上下文获取实例 bid，获取分布式锁，执行对应业务 handler，执行结束后释放锁。锁键包含业务服务命名空间和 bid，例如公会服务与其他实例服务具有各自的锁空间。同一业务实例在不同节点上的请求使用相同锁键，锁范围覆盖 handler 的业务执行。

框架提供锁契约、请求上下文与 Tower Layer 的便捷适配，Redis 是可选的锁实现。用户决定哪些服务或方法需要锁、bid 如何提取、锁实现与参数，以及中间件顺序；也可以替换实现或自行提供 Layer。session 的全局所有权与全局实例的请求级锁分别服务于会话唯一性和实例访问互斥。

## 服务通信与调用边界

不同服务之间通过 gRPC 交互。局外业务中，只有PlayerGateway可以调用 player，player 可以调用其他服务。

内部 RPC 使用标准 gRPC 协议，Rust 实现采用 tonic，protobuf 消息类型和编解码采用 prost。通过配套代码生成工具从 `.proto` 生成消息类型、RPC 客户端和服务端接口。

RPC 基础设施使用 Tower 的 Service 与 Layer 抽象组织中间件，包括超时、并发限制、过载控制、请求元数据检查、实例分布式锁、tracing 和指标。框架提供常用组件和便捷组装 API；用户可以直接使用 Tower 编写或组合自己的 Layer，业务 handler 可独立于这些策略。

session 串行执行、timerSpec 调度和 bid 路由由框架组件负责。RPC 中间件不添加重试层，保持快速失败策略。

其他服务需要通知 player 时，通过封装在 NATS 之上的转发事件进入PlayerGateway，再由 session 驱动 player 处理。按事件类型选择 Core NATS 或 JetStream，见事件投递与重复处理。

RPC 不重试，采用快速失败策略。客户端请求链路上的 RPC 失败转换为协议层 Response 的 ErrorCode，客户端展示错误提示；其他 RPC 调用向调用方返回失败。

RPC 超时视为系统级错误，打印日志并按上述规则返回失败。当前不额外等待原 handler 完成，不提供超时回滚或结果追踪，session 按正常流程继续处理。这是当前明确接受的异常处理边界，串行驱动约定不包含超时后仍在远端运行的异常任务隔离保证。

所有权和请求级锁均不承诺异常路径下的绝对互斥。租约失效或有效性不确定时停止发起新调用；Redis 获取、续租及 session 发起业务前，根据操作开始时刻与本地单调时钟作保守期限检查。检查后仍可能发生进程暂停、网络延迟或租约过期，系统接受时间检查与实际副作用之间的竞态窗口，不默认逐次远程校验，也不强制所有存储写入携带 fencing token。后续存储封装在写入前检查调用期限和本地已知租约期限，超时或有效性不确定时拒绝写入，作为尽力保护。资产等业务仅在有明确需求时增加幂等键、条件更新或事务；当前存储层尚未实现，不据此承诺已有写入保护。

RPC 不重试与 JetStream 的事件重新投递分别处理。消息补发只重发已编码的下行消息，不重新执行 RPC；事件消费按该类型的投递与重复处理策略执行。

提供 HTTP 等外部接口的服务，通过 RPC 或事件访问其他服务，并遵守相同的调用边界。

开发时应避免服务交互形成环。涉及多个实体的一致性流程由业务自行处理，例如按 ID 排序后加锁；当前不在框架中设计通用的跨实体事务或补偿流程。

### 服务配置与中间件组装

服务配置包含启用服务、业务服务注册及对应的中间件链。服务描述节点职责，中间件链描述某项服务或方法的执行策略，两者分别组装。例如一个游戏节点承载 player 和公会实例服务，公会服务配置按 guild id 加锁，player 仍遵循 session 串行驱动约定，不自动套用公会的加锁策略。

客户端 RPC 请求经协议解码与服务分发后，框架提供业务调用上下文，包含服务身份、方法、目标 bid 和追踪信息，供业务中间件使用。示例链路为：

```text
gRPC 接入 → 解码与服务分发 → 业务调用上下文
         → 用户组装的中间件链 → 业务 handler
```

中间件选择、顺序、作用范围和参数由用户控制，可以通过 Rust 代码组装，也可以由配置选择用户已注册的组件与参数；具体配置表达与 API 在实现 RPC 调度时确定。框架负责统一契约、生命周期和易用的适配，不把某条固定中间件链作为所有服务的强制实现。当前游戏配置仍采用既定的无自动重试、快速失败策略。

锁契约放在基础接口层，具体分布式锁后端属于 tok-infra，服务端 Layer 适配属于 tok-rpc，游戏通过 tok 组装。RPC Layer 依赖锁抽象，由用户注入实现，不直接绑定 Redis。当前 ServiceConfig 只有服务名和端点引用；RPC 强类型分发、连接复用和 TowerHandler 代码组装已实现，中间件配置表达、锁后端与锁 Layer 后续实现。

### 多业务实体的隔离

服务处理多个 bid 时，不自动为每个业务实体创建独立的对象、任务、内存或资源隔离。用户按业务需要选择隔离策略，框架提供可组合的抽象与组件。并发互斥可以通过服务配置统一按 bid 加锁，同一个 bid 串行，不同 bid 可以并发；业务数据和读缓存按 bid 区分，访问与状态组织由业务实现。

并发限制、队列或配额可用于服务或实体范围的资源控制，具体能力后续实现，用户决定作用范围。需要进程或部署级资源隔离时，用户调整服务组合并独立部署。按 bid 加锁只提供互斥，不等同于内存、CPU 或故障隔离。player 使用既定的按 player id、全局唯一 session 串行驱动策略。

## 事件模型

跨服务事件封装在 NATS 之上，并分为广播事件和转发事件。两类事件支持相同的目标描述：自定义频道 ID、所有人或指定目标。原来的组目标按频道订阅理解，player 加入哪些频道，就匹配这些频道的消息。

跨节点事件完全异步，生产者不等待目标 player 的业务处理结果，也不要求目标服务回传业务确认。本地事件同步处理。事件类型声明即时或持久化投递策略；消息系统内部的存储或消费确认不作为同步业务回应暴露给生产者。

### 广播事件

广播事件用于直接向客户端发送消息。player 或其他服务都可以通过广播事件通知客户端。

发送内容必须是客户端可识别的消息，通常是 protobuf notify 或 dispatch 消息的封装。

```text
player 或其他服务
    → 广播事件
    → 目标客户端
```

广播事件面向客户端，不触发 player 业务执行。局外投递由网关将消息放入目标 session 的下行发送序列，获得该 session 的 server_seq 并进入补发缓存，然后经接入适配器发送给客户端。下行序列统一组织 Response 与 Notify 的发送，具体订阅和分发机制在实现时细化。

### 转发事件

转发事件用于通知 player，由PlayerGateway接收并通过 session 转发到 player。

对离线 player 默认不拉起，业务可以选择允许拉起。登录时恢复相关业务状态是主要业务模式。

```text
其他服务
    → 转发事件
    → PlayerGateway session
    → player 服务
```

### 本地事件

本地事件在当前 player 调用中同步执行，用于内部模块解耦，不重新进入 session 队列，也不作为独立任务并发执行。可以统一事件类型与注册抽象，但不经过 NATS。

本地事件没有与客户端 Response 配对的语义。Response 始终与 Request 成对；本地事件只是 player 内部的调用与解耦手段。

### 事件投递与重复处理

按事件类型声明投递策略，跨节点业务交互保持完全异步。加载离线玩家是独立选项，不意味着必须持久化投递。

| 策略 | 实现 | 适用事件 |
| --- | --- | --- |
| 即时投递 | Core NATS，允许未投递成功，默认不积压 | 频道广播、刷新提示、登录可恢复的业务通知 |
| 持久化投递 | JetStream，后台组件管理存储确认与消费确认 | 确实需要保存并在故障后继续处理的事件 |

Core NATS 是至多一次投递，JetStream 可提供至少一次消费并发生重新投递；选择取决于是否需要持久化恢复，而非单纯要求避免重复。[Core NATS 说明](https://docs.nats.io/learn/core-nats/)、[JetStream 消费说明](https://github.com/nats-io/nats.docs/blob/master/nats-concepts/jetstream/consumers.md)

所有跨节点事件携带稳定 event_id，重复发布同一次事件沿用该 ID。JetStream 将其映射到 Nats-Msg-Id，抑制配置窗口内的重复发布，但这不等同于业务处理去重。[JetStream 消息头说明](https://github.com/nats-io/nats.docs/blob/master/nats-concepts/jetstream/headers.md)

重复处理以业务幂等为主，框架去重为辅，分为三类：天然幂等事件重复执行无害；允许有限窗口去重的事件由组件按 event_id 与目标使用有界内存记录过滤；资产等不可重复的业务通过业务操作 ID 或版本做幂等，记录与业务变更一起提交。内存过滤不能保证跨进程退出或网关交接后的业务唯一执行。不要求所有事件访问 Redis 去重。

持久化转发事件成功处理后由后台组件确认，只进入网关内存队列不代表 player 已处理。处理成功但确认前发生故障仍可能重复处理，因此需要上述业务幂等。默认不加载的离线目标按规则跳过，并完成对应消费，不等待其下次登录，也不因事件持久化而自动获得离线消费资格。

## 消息链路约定

| 链路 | 当前约定 |
| --- | --- |
| 客户端 request | 服务器必须给出对应 response，非预期错误通过 ErrorCode 表达 |
| 服务端 dispatch 或 notify | 服务端主动向客户端推送 |
| 其他服务通知 player | 使用转发事件，经PlayerGateway和 session 处理 |
| player 或其他服务通知客户端 | 使用广播事件 |
| 其他服务之间交互 | 使用 RPC，不重试、快速失败，并避免形成调用环 |
| HTTP 等外部接口服务访问内部业务 | 使用 RPC 或事件 |

Response 始终作为请求的协议回应，非预期错误也通过 Response 的 ErrorCode 表达。断线时，已生成的 Response 进入补发序列；客户端收到后展示相应结果，不通过框架自动重试 RPC。

未完成请求由客户端按时间管理等待状态，超时展示转圈或网络恢复提示，并按退化策略尝试重连、快速重登，最后回主界面全新登录。框架不额外追踪或重试未知结果的请求。

## 客户端协议与业务扩展

框架提供接入适配、消息封装、协议注册与分发，以及客户端上下文；具体游戏定义 protobuf 消息和业务处理函数。bid 用于业务实体路由，消息 ID 用于识别消息类型和选择处理函数。

逻辑消息包含 Request、Response 或 Notify 类型、消息 ID、请求序号，以及具体游戏定义的 protobuf 消息体。Response 通过请求序号关联 Request，并可以包含 ErrorCode。接入适配器负责映射这些语义：例如 TCP 实现可以使用长度字段分帧，HTTP 实现可以将路由、请求头和消息体映射成逻辑消息。具体字段布局后续确定。

PlayerGateway解析消息外层，根据 session 中的可信 player id 调用 player 的通用 gRPC 入口，传递消息 ID 和 payload。player 侧的注册适配层解码具体 Request、调用强类型业务处理函数，再编码 Response。timerSpec 属于内部返回信息，由 session 消费，不直接包含在客户端业务回应中。

框架提供强类型通知接口，由适配层负责消息 ID、编码及广播事件封装。游戏维护稳定的消息 ID 和 Request 与 Response 的配对关系，处理函数及请求回应配对仍显式注册。示例将 ID 集中在游戏 proto 的 MessageId 枚举中，按 MESSAGE_ID_<消息类型的 UPPER_SNAKE_CASE> 在构建期关联顶层消息，生成 GameMessage::MESSAGE_ID；数字缺失、重复或名称不匹配时构建失败。零表示未指定，既有编号保持稳定，删除时 reserved 编号与名称。运行时仍按数字分发，ID 名称不决定处理权限、服务归属或请求回应配对；框架本身不依赖游戏枚举。通用分发表生成另行扩展。

登录认证通过业务扩展点验证凭证，网关取得可信 player id 后获取 session 所有权。局内可以复用编解码与消息映射组件，同时保留异步消息模型和独立的协议封装。

## 短线重连与消息补发

本节描述恢复与交接设计。当前已实现在线 timer、统一下行序列、ACK、有界缓存及同网关 token 恢复，默认断线宽限期 30 秒；跨网关交接尚未实现。版本 3 的协议、连接代次、凭证有效期及退化边界见[局外 TCP 协议与 session 实施约定](client-session.md#第三批第三步同网关恢复)。

重连恢复原逻辑会话。客户端保留界面、业务状态和未完成请求，暂停新的业务请求，可展示网络恢复提示。正常短线重连不经过 SDK 鉴权，也不执行完整登录流程。

### 连接与会话生命周期

Connection 表示一次传输连接或接入绑定；session 表示玩家逻辑会话。session 不依赖某一条 socket 存活，HTTP 请求也可以通过认证后的会话标识进入同一个 session。

对于持续连接的接入方式，断线后 session 在可配置的宽限期内保留所有权，继续串行处理 timer 和事件，并缓存下行消息。宽限期结束后才进入离线处理模式。HTTP 适配器报告会话活动，由会话组件根据配置管理有效期，不把单次 HTTP 请求结束视为玩家断线。

服务器签发 resume_token，关联玩家、逻辑会话及有效期。当前同网关实现使用有界内存中的随机不透明凭证，默认身份有效期 1 小时；新登录轮换并撤销同玩家旧凭证，恢复不刷新期限。网关重启后凭证失效，其他网关暂不能验证；跨网关交接阶段需补齐凭证共享或签名验证机制。

客户端在新接入上提交 token，服务器验证后恢复会话。同网关重连复用保留的 session；后续跨网关重连获取或交接 Redis 中的 session 所有权，并失效旧连接。

token 的身份有效期与 session 的可恢复窗口分开。session 无法恢复时，仍有效的 token 可以用于快速重登，从登录协议开始恢复业务，无需重新进入 SDK 鉴权。重复登录或快速重登按会话状态处理 epoch 与旧 session；仅恢复原会话时保持原 session_id 和消息序列。

### 消息序号与确认

| 字段 | 职责 |
| --- | --- |
| session_id | 标识逻辑会话，跨连接保持 |
| request_id | 关联 Request 与 Response |
| server_seq | 标识同一逻辑会话中的服务端下行消息顺序 |
| ack_seq | 客户端连续处理完成的最大 server_seq |
| resume_token | 服务器签发的凭证，支持重连及有效期内的快速重登 |

局外 Response 和 Notify 进入同一个下行序列，包含已绑定 session 的业务失败回应。序号按发布顺序递增，request_id 只关联请求与回应。客户端在消息已连续应用到业务状态后确认；第三批第二步采用独立 Ack，暂不增加上行业务消息携带确认的第二种方式。重复收到已处理的序号时忽略其业务内容。握手、重连和确认等控制消息不占业务序号，也不作为业务消息等待补发完成后才处理。客户端 Frame 版本已升级为 3，客户端与服务器同步升级。

服务端接受当前连接绑定 session 的累计确认，忽略零值、重复或倒退值，拒绝超过已发布最大序号的确认；确认上界不依赖 socket 写入完成记录。ACK 表达客户端处理进度，不证明客户端确实处理过消息，不提供请求幂等保证。

服务端先将带有 server_seq 的消息字节写入内存补发缓存，再尝试发送。缓存受时间、消息数量和字节容量限制。重连根据客户端 ack_seq 补发尚未确认的消息，沿用原 server_seq，不重新执行业务或重试 player RPC。

帧尺寸检查及超大回应转换在分配序号与缓存提交前完成，发送层不能再改变缓存的正文。ACK 释放已确认记录；时间或容量超限从最旧记录开始淘汰，允许淘汰未确认记录，避免慢客户端造成无界内存占用。仅当客户端确认位置之后至当前最大序号的缓存完整连续时才能补发，缺口返回 ResumeUnavailable；不能静默跳过缺失消息。缓存淘汰本身不使在线 session 立即关闭。

补发期间产生的新消息进入同一序列，不能越过待补发消息。服务器发送恢复完成标记，客户端按序处理到该标记后恢复普通交互。

### 跨网关获取补发记录

补发消息字节保存在网关本地内存，生产环境也不将其写入 Redis。Redis 用于 session 所有权管理，跨网关重连时，新网关通过内部 RPC 直接向旧网关获取补发字节及相关会话状态。

交接需要保持原 session_id、消息序列及确认位置，并处理 timerSpec 调度状态、未完成请求和交接期间的消息。旧网关停止驱动与新网关开始驱动之间需要明确交接边界，确保最终回应与新产生的通知不会遗漏，且只有当前所有者驱动 player。具体交接 API 和顺序在实现阶段细化。

补发缓存保存逻辑消息编码后的字节，位于接入协议专属封装和加密之前。新接入使用自身的协议与安全上下文发送补发内容，不复用旧连接的密文或流量密钥。

JetStream 的服务间事件确认与客户端 ack_seq 分别管理。网关已消费事件不代表客户端已处理对应通知，客户端补发由会话下行序列负责。

### 无法补发时的处理

旧网关不可用、会话已过期或缓存窗口不完整时，返回明确的 ResumeUnavailable。token 仍有效时，客户端使用该 token 快速重登，从登录协议开始重新获取业务状态和 timerSpec，并建立新的逻辑会话及下行序列。客户端尽量表现为当前界面刷新，而非回到登录界面。token 失效或退化流程失败时，才回主界面全新登录并重新鉴权。

原网关内存记录丢失时，框架不保证继续原消息序列。短线补发、业务状态重同步和完整登录分别作为不同恢复路径。

本节定义局外消息接续。局内是否补发、哪些消息需要补发以及重连后的场景恢复方式，由局内接入和场景协议后续确定，不强制套用局外的下行序列。

## 接入协议与安全组件

传输协议、消息编码和安全机制分别提供可替换的组件。框架按配置和客户端能力组合组件，具体游戏业务处理函数不依赖所选网络协议或加密方案。

安全组件可以使用 TLS、DTLS，也允许网关提供自己的消息级加密实现，负责相应的握手、密钥管理、加解密、完整性校验和防重放。自有实现使用成熟密码算法和库；是否采用某种机制、具体协议版本及客户端兼容范围在实现选型时确定。

不同安全机制的接入位置不同：TLS 属于流传输安全，DTLS 属于数据报安全，消息级加密作用于消息封装。通过对应适配器组合，不要求所有机制具有相同的字节处理顺序。开发环境可以选择明文适配，生产配置明确所用安全机制。

恢复逻辑会话与恢复安全上下文分别处理。新接入按选定安全机制建立或更新安全上下文，session 不迁移旧连接的流量密钥，业务层仍通过同一客户端上下文处理请求和通知。

接入适配器需要声明其支持的能力，包括请求回应、主动下行及消息接续。HTTP 接入需要通过轮询、长轮询、SSE 或其他配套下行方式承载 Notify 与补发；具体方式由实现选择。

接入适配器报告连接或通道状态，会话组件统一管理逻辑会话与串行执行。认证后的多个 HTTP 请求进入同一 session，不因传输允许并发而并发执行 player 业务。

## 存储与缓存

缓存采用 Redis Cluster，数据库采用 MongoDB 集群。

存储层独立于业务层。存储 API 由业务层定义，存储层提供实现，以避免业务与具体存储技术强耦合。

player 可以使用读缓存。存储层后续单独设计，缓存失效、持久化时机、事务边界和版本校验不属于当前设计范围。

## 服务注册与发现

生产环境强依赖 Kubernetes。开发环境支持单二进制单进程运行多个服务，也支持同一二进制按配置拆分为多个开发进程。服务发现提供单进程 Memory、多进程开发 Redis 和生产 Kubernetes 后端，不引入独立的 etcd 注册中心。

### 生产环境

以 Pod 作为部署节点的基础，一个 Pod 中的游戏进程可按配置承载多个服务。node_id 可使用 Pod UID，通过 (node_id, service_name) 定位服务；Pod 内进程重启的启动代次单独标识，具体身份获取与注册校验在发现实现时补齐。

部署组合由用户决定，例如PlayerGateway独立部署、游戏节点组合 player 与公会等低频服务、场景节点独立部署。一个服务处理多个 bid，不为每个业务实体创建 Pod。组合在同一进程的服务共享进程资源与故障边界，并随同一个部署节点扩缩容；需要独立扩缩容或资源隔离时可以拆分部署。

服务实例通过 Kubernetes 部署和 Service 配置暴露。发现组件采用 informer 或等价的监听与本地缓存机制，获取 Service 对应的 EndpointSlice，维护实例地址、端口和就绪状态。

发现结果关联部署节点、节点提供的业务服务及其端点。业务路由先按服务筛选可用节点，再按 bid 选择节点；具体索引与缓存结构由后端实现，不要求所有服务共享相同端口。

监听端点与业务服务独立配置。节点通过 endpoints 声明端点名称、协议和监听地址，业务服务通过 endpoint 引用端点；多个服务可以绑定同一端点，也可以按需分别绑定。通常 player、guild、mail 等内部服务共享一个 gRPC 端点，网关客户端接入使用另外的端点。协议名由传输实现解释，可扩展，传输参数及加密组件在接入实现时设计。

共享端点由节点的传输组件统一创建和管理，每个端点只启动一次监听；业务服务注册到对应端点，gRPC 按协议中的服务名和方法分发。业务 service_name 与 protobuf 服务的绑定由组装层明确，不能假定二者字符串天然一致。每个服务仍独立配置中间件、锁和并发限制。当前 RpcEndpoint 已支持显式绑定不同 protobuf 服务，Application 统一监听和监督，业务初始化后才开启对应就绪入口；同一端点拒绝重复 protobuf 服务名。普通业务通用入口 BusinessRpc 在一个端点只能绑定一次，多个普通业务服务可使用各自的 protobuf 服务；多业务注册到同一通用入口的调度另行扩展。生产发现发布可访问的节点地址，监听配置中的通配地址不能直接作为远程连接目标，地址转换随 Kubernetes 发现实现补齐。

需要 bid 亲和的 RPC 由路由组件选择实例，使用选中的实例地址建立连接。

### 开发环境

同一进程中的服务共享内存服务目录。服务启动时注册服务信息，停止时移除，调用方通过相同的发现接口获取节点信息，无需依赖 Kubernetes。

Memory 仅用于单进程开发与测试。多进程联调使用 Redis 开发后端：每个进程配置唯一 node_id，共享同一 namespace；服务就绪后发布带 TTL 的节点服务列表，后台续租并刷新本地缓存，正常退出条件注销，崩溃后过期摘除。更新、续租与注销均检查独立实例 token，防止旧进程修改重启后的记录。初期周期扫描，不依赖 Pub/Sub；发现同步或租约失败使应用退出，重新启动后恢复。该后端不承担 session 全局所有权。

端点 address 用于监听，advertise_address 用于发布；省略后者时使用监听地址。Redis 开发发现禁止发布通配地址，跨开发机必须填写可访问的 IP。工厂通过 ServiceContext.listen_address 绑定，ServiceContext.service.address 提供发布地址。完整参数、隔离与错误边界见 Rust 用户指南；redis-game.toml 和 redis-gateway.toml 提供双进程示例，just redis-test 与 just redis-smoke 验证真实 Redis。

### 发现与路由边界

各发现后端提供统一的节点快照和变更通知。ServiceRegistry 负责异步发布和条件撤销，ServiceDirectory 只读取本地缓存。服务描述包含 node_id、service_name 及绑定端点的协议、地址（含端口），按服务名查询节点快照；一个进程启用多个服务时，可以提供多条服务描述，共享端点的服务具有相同协议和地址。

bid 路由独立于发现后端，由路由组件根据节点列表选择目标。session 所有权仍由 Redis 管理。

具体服务描述、Kubernetes 资源映射和节点变化后的路由行为在实现时细化。

## 构建与部署

整个游戏最终输出一个二进制，包括网关和游戏服务。通过不同配置，使同一二进制具备不同的服务属性。

目标平台为 Windows amd64 和 Linux amd64，amd64 对应 Rust 的 x86_64 架构。两个平台分别构建可执行文件，各平台内使用同一个二进制承载不同服务。

依赖选型、文件路径处理、进程退出和开发命令都需要兼容这两个平台。Linux 的 GNU 或 musl 工具链及最低系统版本在构建方案中另行确定。Rust 工程建立后，构建与测试覆盖两个目标平台。

项目命令统一通过 just 1.58.0 组织，仓库根目录的 `justfile` 作为开发入口。提供 check、test、fmt、fmt-check、clippy、proto、docs、build、run、smoke、rpc-smoke、client-smoke、config-check 和 verify；底层 Rust 构建工具使用 Cargo，CI 也通过 just 执行常规检查。用户指南作为 tok crate 的 rustdoc 首页，API 文档由 Rust 注释生成，示例通过文档测试验证；CI 构建并保存 HTML 文档。

服务在逻辑上分离，使用同一个二进制并不要求所有服务运行在同一个进程中。初始配置采用 TOML，支持声明节点、发现后端和多个服务，并在启动前校验。组装层通过 ServiceFactory 按 service_name 注册实现，Application 管理初始化、运行监督及退出。本文服务分类描述业务职责，不对应框架内置枚举，也不决定锁、中间件或执行方式；这些由用户配置。

开发环境按配置顺序初始化服务，初始化成功后才注册到内存服务目录；默认单服务初始化期限为 30 秒。初始化必须可取消，资源通过 RAII 释放，服务不得遗留脱管任务。运行任务持续执行，收到取消通知后停止接收工作并清理资源。初始化失败或超时、服务运行失败、提前结束或崩溃均触发进程退出，撤销已注册服务并通知所有已启动服务清理。默认整体协作退出期限为 10 秒，超时中止剩余任务并返回错误；游戏可调整期限。

Windows 使用 Ctrl+C，Linux 使用 Ctrl+C 或 SIGTERM。示例提供 --run-for 用于自动化退出验证，CI 通过 just smoke 执行，just rpc-smoke 验证内部调用，just client-smoke 经真实 TCP 验证登录、状态读写和 player 调用 guild。示例监听共享内部 gRPC 和客户端 TCP 端点。应用先准备内部监听，工厂初始化后发布服务并开启对应 RPC 入口；TCP 监听由网关工厂初始化并交给监督任务。工厂不能在初始化中等待尚未启动的其他服务，就绪后的依赖调用在运行阶段发起。

资源隔离是必要要求。容量控制、运行指标和可观测能力在开发过程中补齐，不作为当前设计推进的阻塞项。

当前实现包括八个框架 crate、示例游戏、TOML 配置验证、内存目录、Redis 开发发现与合并变更通知、bid 亲和路由、Memory 与 Redis session 所有权、服务生命周期、可观测组件、protobuf 生成、共享内部 RPC、客户端 TCP 分帧与注入认证、有界串行 session、timer 更新与调度、下行通知、rustdoc 用户与 API 文档、just 命令和 CI。示例 player 和 guild 共享内部端点，客户端网关经认证身份完成状态读写、计时更新状态和 player 到 guild 的调用；独立网关与游戏进程可通过 Redis 开发发现联调，多个网关可显式共享 Redis 所有权。ServiceContext 可注入发现查询后端，生产 Kubernetes 配置可验证但后端运行仍报尚未实现。Redis Cluster 客户端、跨网关交接、NATS、补发及安全适配后续实现；内存所有权不提供跨进程协调，Redis 租约不承诺异常路径下的绝对互斥，内部上下文字段校验不代替调用身份认证。部署目录暂不提供可运行的 Kubernetes 清单。

## 可观测约定

日志使用 tracing 和 tracing-subscriber；开发环境默认文本格式，生产配置使用 JSON 输出到 stdout，由 K8s 平台采集。日志规则支持按模块过滤，RUST_LOG 覆盖初始配置，LogControl 支持读取及运行时更新过滤规则，错误配置保留原规则。控制句柄可供后续管理接口或配置监听器使用。

指标使用 metrics 和 metrics-exporter-prometheus，由独立 HTTP 端口提供 /metrics，Prometheus 拉取。指标标签使用服务、消息类型、结果等有限维度，不使用 player_id、bid 或 request_id。已提供服务启动次数、初始化耗时、运行服务数和运行失败次数。指标 HTTP 服务使用 axum，随可观测组件退出，服务不各自初始化全局 recorder。

追踪使用 tracing-opentelemetry、OpenTelemetry SDK 和 OTLP gRPC exporter，对接 Collector，后端由部署环境选择。日志过滤、追踪过滤和采样分别配置；动态调整日志级别不改变追踪采集。采样优先级为：强规则命中直接采样，否则有效父级决定优先，否则普通根 span 通过 trace_filter 后按 ratio 采样。JSON 日志在有效追踪上下文内输出 trace_id/span_id。

强追踪规则按 span 名称、target 和创建时提供的字段精确匹配，单条规则条件为 AND，多条规则为 OR，字段支持字符串、数字和布尔值。空规则或非法字段配置被拒绝。TraceControl 支持读取配置、整体更新采样配置、单独替换强规则列表，校验失败保留原配置；新配置影响后续采样决定，已经开始的 span 不重新采样。

强追踪规则不受普通 trace_filter 和 ratio 排除，并能覆盖未采样父级的决定；已采样父级的后续 span 沿用采样，不被 trace_filter 截断。为了在采样时读取字段，span 先进入 SDK，普通根 span 的级别和模块过滤在 sampler 中执行；trace_filter 使用级别和模块语法，字段条件通过强追踪规则表达。

强规则尽量在请求入口根 span 判断，采样字段必须在决定前提供；采样后补录字段不能改变决定，下游强制开启无法恢复此前被丢弃的上游 span。强制采样解决采集选择，不提供故障时的数据送达保证。

每次请求、事件或 timer 执行建立独立 span，不以整个 session 生命周期作为长期 trace。gRPC metadata 已传播 W3C TraceContext，NATS headers 随事件组件实现，异步事件可使用 span link。token 和协议正文默认不记录，bid 可作为日志或 span 字段。

可观测组件由游戏入口初始化一次，默认仅开启日志，指标监听与追踪导出按配置启用。服务退出后关闭指标监听并刷新追踪，刷新有超时限制，不阻塞异步调度线程。现阶段不部署日志采集器、Prometheus 或 Collector；集成测试通过临时指标端口及模拟 OTLP Collector 验证导出。

## 后续设计与实现边界

| 内容 | 当前处理方式 |
| --- | --- |
| session 全局唯一 | 作为执行模型前提，线上计划通过 Redis 管理所有权，跨网关重连先获取所有权 |
| 离线 player 事件 | 默认不拉起，个别业务可选择拉起，大部分业务在登录时恢复 |
| player timer | 登录提供全量 timerSpec，后续可选增量更新，session 调度；错过周期合并触发，交接沿用调度 |
| 全局实例互斥 | 采用请求级锁，可以提供 Redis 锁库组件 |
| 跨服务事件 | NATS 异步投递，频道匹配，默认不消费离线事件；按类型选用 Core NATS 或 JetStream，业务幂等为主、组件去重为辅 |
| RPC 失败 | 不重试、快速失败；客户端请求链路通过 Response 的 ErrorCode 提示，其他调用向调用方返回失败 |
| RPC 实现 | 标准 gRPC 协议，采用 tonic 和 prost，使用 Tower 组织 RPC 基础设施与中间件 |
| 客户端协议 | 接入协议可替换，框架提供逻辑消息与强类型分发适配，游戏提供 protobuf 消息和处理函数 |
| 短线重连 | token 恢复原会话并按序补发；无法恢复时用有效 token 快速重登，不走 SDK 鉴权 |
| 补发缓存 | 网关本地有界内存缓存，跨网关直接从旧网关获取字节，不写入 Redis |
| 客户端加密 | 安全机制可替换，支持 TLS、DTLS 或网关自有消息级加密实现的适配，具体实现后续选型 |
| 项目命令入口 | 使用 just，由根目录 justfile 统一组织开发任务 |
| 目标平台 | Windows amd64 和 Linux amd64，分别构建并验证 |
| 服务发现 | 生产使用 Kubernetes，开发使用单进程 Memory 或多进程 Redis，通过统一接口读取本地节点快照 |
| 跨实体一致性 | 业务自行处理，例如按 ID 排序加锁，当前不设计通用框架方案 |
| 无缝场景切换 | 保留SceneGateway的未来职责，当前不设计具体协议 |
| 存储细节 | 后续单独设计 |
| 容量与运行指标 | 开发过程中补齐，不阻塞当前设计 |
| 资源隔离 | 必须具备，具体实现随服务部署和运行模型细化 |

服务发现、session 所有权获取与交接、请求级锁、timerSpec 和 JetStream 事件组件的具体 API 在相应实现阶段细化。
